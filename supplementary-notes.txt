What works now
--------------
- Buyer registration and login, with hashed passwords and role checks
- Seller registration and login, with bio and preferred meet-up
- Admin login for the seeded admin account
- Buyer browse screen with keyword search, category/type/condition/price filters and sorting
- Listing detail screen with photos, seller rating, view counter and report button
- Buyer offers, borrow requests and giveaway claims
- Atomic giveaway claim: two buyers cannot both win the same giveaway
- Seller offer management: accept, decline and counter
- Buyer can accept a seller counter offer from My Deals
- Chat panel on the listing detail screen, with retained messages and search
- Buyer deals: return a borrow early and mark a purchase or claim complete
- Borrow scheduler: overdue borrows expire and the listing goes live again
- Seller My Listings: edit/delete only when allowed, with offer-history warnings
- Shared notification board for buyer, seller and admin, with read/unread and category filter
- Sidebar unread notification count
- Password rules: 10 to 64 characters, at least one uppercase, one lowercase and one digit

What is still missing or limited
--------------------------------
- Data is in memory only. Restarting the app resets all accounts, listings, deals and chat.
  This is the same limitation as the original skeleton and was agreed in STEPS.md.
- The JavaFX controllers are not unit tested. They were checked by loading every screen
  in a JavaFX smoke run and by clicking through the flows manually.
- The borrow scheduler checks once per second, but the UI only picks dates, so the
  smallest visible borrow period is one day. The five-second rule was kept as a hint
  and the service does enforce that the end date cannot be before the start date.
- Photos are copied into src/main/resources/images/uploads and the classpath copy.
  This is fine for a local demo, but a real app would use a proper upload folder.
- Reviews and seller ratings are not fully finished yet (step 22 onward). The user model
  already has averageRating and ratingCount, and notifications for reviews exist, but
  the review screen and reply flow are still to come.

How to run the tests
--------------------
From the project folder:

    Windows:
        .\mvnw.cmd test

    macOS / Linux:
        ./mvnw test

At the time of writing the fixed build was run with Java 21. On a Mac I also used:

    mvn test -Djavafx.platform=mac

because the pom defaults the JavaFX classifier to win for the Windows teammate.

Main design decisions
---------------------
- Passwords are hashed with salted PBKDF2. The raw password is never stored.
- Access control is checked in the service layer, not only by hiding buttons.
  SessionManager.requireRole is called from OfferService, DealService and ListingService.
- Giveaway claims are synchronized and re-check the listing status inside the lock.
  This is why two buyers cannot both win.
- View count is incremented when a listing detail screen is opened.
- Chat messages are kept in the in-memory store and searched with a case-insensitive match.
- Notifications are stored with read/unread state so the board and sidebar badge agree.
- Seller edit/delete is centralised in ListingService so the UI and tests use the same rules.

Assumptions
-----------
- There is no backend API. The service/store layer is the API boundary for this project.
- The admin account is seeded and has no registration screen.
- Any seller can only edit or delete their own listing.
- A listing with a pending offer is locked for editing/deleting.
- Offer history does not block deleting an old listing, but the seller is warned first.
- Ratings are whole stars from 1 to 5 in the model; the review UI will be added later.
